# Persistent tool usage statistics (#178)

## 1. Scope

Measure real tool utilization and reliability, compare generation models and find tools that cost model context without being used. The statistics extend the shared `internal/statistics` collector as one more persistent dataset (`tool_usage`); general statistics stay ephemeral and the interaction dataset (#182) is independent. Everything is an aggregate: no tool arguments or results, message content, prompts, user attribution, call/run IDs, per-call traces or per-invocation timestamps (only the observation-period start and the snapshot save time are persisted).

## 2. Observation boundary

One observation per conversation turn, recorded in `runConversationTurn` immediately after the generation/tool loop ended and **before** any final Telegram text delivery, on every exit path (success, intentional silence, failure, cancellation, timeout, loop exhaustion). Its input is the authoritative runtime result (`tooluse.Result`): the `ToolCallRecord`s and `AdvertisedTools`, never best-effort events. The tool statistics epoch is captured before the run; a reset while the turn is in flight drops the whole turn (advertisement and calls).

The observation carries the chat, the mode (`explicit` or `proactive`, from the turn trigger), the **effective** generation model (the chat override, otherwise the environment route model, wired unconditionally), the advertised set, the call facts and a run-failure class. The run-failure class (`timeout`, `cancelled`, `generation`) describes the generation/runtime outcome at the observation point only; it does not include final delivery failures, which interaction execution statistics own.

## 3. Counting semantics

- **Advertised turns.** A tool counts once per turn if it was advertised in at least one generation request that was actually submitted (an iteration whose request preparation failed contributes nothing). Dynamic availability changes inside a turn never add a second count.
- **Attempts** are the returned records, independent of advertisement. Calls skipped after an accepted terminal completion (`say_nothing`) or after a context-done abort have no record and are not attempts.
- **Rejected** calls never reached their handler, by reason: `not_registered` (hallucinated names), `not_advertised`, `unavailable`. **Executed** calls reached it: `succeeded` counts `ok` and valid `empty` results (a valid empty search is a success; `succeeded_empty` is the sub-count), `failed` counts `error` results (invalid arguments are an executed failure because handlers validate their own arguments). An unrecognized status counts as failed with class `other` and the `status_unrecognized` disclosure.
- **Errors** (rejected and failed) are counted by stable error class (`invalid_arguments`, `not_found`, `unavailable`, `rate_limited`, `permanent`, `transient`, `cancelled`, `ambiguous_outcome`, `other`) and by bounded error code.
- **Side effects** are counted for side-effecting tools only: `confirmed`, `not_applied`, `unknown`. They come from the record, which exists before result serialization, so a result-preparation failure or a later run failure never erases a confirmed effect. A successful `say_nothing` is a success with no side effect.
- **Result preparation** (`complete`, `reduced`, `failed`) is counted separately from handler outcome and does not claim delivery: a terminal completion, cancellation or loop exhaustion can end the run before any later request carries the result. A preparation failure is not an execution failure and triggers no retry/recovery accounting; `repeats_after_preparation_failure` makes later calls visible.
- **Utilization** is `advertised_invoked_turns / advertised_turns`: the turns in which the tool was both advertised and invoked. Calls to tools that were not advertised increase attempts but not the numerator, so the rate never exceeds 1. Rates are `null` (not 0) when their denominator is 0.
- **Retries and recovery** describe observable later calls of the same tool inside one turn, within a batch and across iterations, in record order; they make no claim about model reasoning. A retry is any call of a tool after an earlier rejected/failed call of it; a recovered call is a retry that succeeded. `failure_identity_turns` counts (tool, turn) pairs with at least one error; `recovered_identity_turns` those with a later success. Matching uses the **original** tool identity before folding, so a failure of tool A followed by a success of unrelated tool B is never a recovery even when both fold into one overflow row. On folded rows the identity-turn counts can exceed unique turns; the export labels them as identity-turn counts. The other turn counters (`advertised_turns`, `advertised_invoked_turns`, `invoked_turns`) are unique turns per row, deduplicated after folding.
- **Latency** is a histogram of executed calls only (13 edges, 10 ms – 120 s, open-ended top bin); percentiles are histogram approximations.
- **Zero-use tools.** Registered tools appear with zero counters and are flagged `never_advertised` (no turn advertised them, e.g. decision tools without System One) or `advertised_unused`. A tool with persisted data that is no longer registered stays with `registered=false`.

## 4. Keys and cardinality

Tool rows are keyed by `{tracked name | other_registered | unregistered}`; the overflow kinds are tags, never names, and cannot collide with a real tool called `other_registered`. At most `MaxTrackedTools` (128) registered names are tracked; further registered tools fold into `other_registered`, every hallucinated name into `unregistered` (raw names are used only for in-turn matching and are never stored or exported). The catalog (registered names in registration order, set after all tools are attached) fills the tracked slots after restored names; the snapshot discloses catalog size, tracked and omitted entries, and zero-use rows exist only for tracked catalog tools.

Chats (32) and models (8, 128-byte IDs) have their own tracked sets, with overflow tags and oversized-identifier folding without truncation. Two projections carry the same full row (counters, error classes, error codes, latency histogram): `by model × mode × tool` (the exact global view and model attribution) and `by chat × mode × tool` (per-chat view); a chat × model × tool cross product is not kept, so per-chat model attribution is unavailable. Error codes must match `[a-z0-9_]{1,48}` (otherwise `other`), are interned in a dataset-wide dictionary of 64 and admitted per tool key up to 16 distinct codes, decided once per (tool key, code) before either projection is updated, so both projections fold identically whatever the arrival order. Snapshots disclose `per_chat_complete`, `model_attribution_complete` and oversized folds.

## 5. Persistence

Same mechanism as the interaction dataset: a whole-row snapshot per dataset in `statistics_snapshots` (`tool_usage`, format version 1), `(generation, revision)` dirty tracking, conditional upsert, validated restore, atomic quarantine, newer-format protection, bounded final flush and the reset acknowledgement rules described in `interaction_statistics.md` §6. Restore validates dictionaries and caps, reference integrity, row invariants (succeeded + failed = executed; executed + rejected = attempts; error classes and codes = failed + rejected; latency total = executed; advertised-and-invoked ≤ advertised and invoked), per-tool code admission, per-code and per-counter equality between the two projections, and turn-counter agreement. There is no interrupted-operation reconciliation: tool turns are recorded atomically at turn end, and a turn in flight at termination contributes nothing. `ResetToolUsage` starts a new generation and is independent of the general and interaction resets; a reset keeps the registered catalog rows as zero-use.

**Durability.** While saving succeeds, an abrupt termination loses the observations since the last successful save (30 s ticker plus one in-progress write); a graceful stop closes admission, joins the loop and any in-flight write (never abandoning them), then runs the final flush under a 5 s budget; an overrun of that budget is reported, not hidden. During a write-failure streak nothing is discarded and the loss window extends to the streak's start. A failed reset write followed by a crash before successful persistence restores the previous dataset.

**Bounds** (derived and asserted by tests from the real constants): at most 10,920 rows (9 × 2 × 130 model rows, 33 × 2 × 130 chat rows); the strict worst-case payload (maximum-width counters everywhere) is bounded by about 18 MB and about 4 MB of counters in RAM; the measured saturated payload is about 12 MB, below the 32 MiB write limit that is also applied on read. Realistic deployments stay in the tens of kilobytes.

## 6. Administration

The statistics screen offers global and per-chat tool statistics, a JSON export (`tg-llm-bot/tool-statistics`, version 1), a PNG report and a dedicated confirmed reset, all behind the existing admin access control. JSON and PNG are rendered from one immutable snapshot and delivered independently; a render failure keeps the JSON.

The primary PNG chart is a horizontal stacked bar chart of successful and unsuccessful (rejected + failed) invocation attempts per tool, one row per tool, descending by attempts, with totals; zero-use tools fill any remaining rows up to a bounded row count and the footer discloses omitted tools. Advertisement counts, utilization, failure classes, recovery rates, latency summaries and model attribution are reported numerically.

## 7. Tests

Counting (advertisement once per turn, dynamic availability, rejected vs failed, empty results, `say_nothing`, terminal completion, repeats and recovery including folded identities, ambiguous side effects, preparation failures), attribution (effective model, mode, global vs per-chat), zero-use and never-advertised tools, cardinality and tagged overflow, error-code folding across arrival orders, persistence round trips and malformed payloads, reset races and independence, concurrent collection/persistence/resets, worst-case size, JSON privacy, PNG rendering and admin access control.
